and the two site publishers (`publish-naranjo-online-image.yml`,
`publish-lidersea-com-image.yml`).

## 2. Release identity: machine-strong, human-thin

- CONFIRMED there are **no git tags and no GitHub Releases** in the
  repository (zero `refs/tags` via `ls-remote`; releases page empty
  follows). Version identity lives only in `websites/*/VERSION` files and
  OCI tags; publication triggers on path-filtered pushes to `main`, not on
  tags.
- CONFIRMED publisher flow: build → push working tag `sha-<commit>` →
  verify digest → promote a stable `vX.Y.Z` tag (scripts under
  `scripts/ci/`). The `sha-*` tags remain on the package permanently.
- CONFIRMED GHCR presentation today (anonymous):
  `naranjo-online`: `v0.1.2`, `v0.1.3`, 3× `sha-<40-hex>`, 3×
  `sha256-<64-hex>`; `lidersea-com`: `v0.1.2`, `v0.1.3`, 2× `sha-*`, 2×
  `sha256-*`. A visitor sees more opaque tags than meaningful ones.
- INFERRED the `sha256-*` entries are attestation/referrer artifacts from
  provenance/SBOM publication; they are load-bearing for verification, not
  junk, but they dominate the page visually.

## 3. Human-facing gaps (CONFIRMED)

- README carries **zero badges** — no build status, no CodeQL, no coverage
  signal. CI computes rich state that is invisible at a glance.
- **No coverage measurement anywhere** in CI (no Go `-cover`, no frontend
  coverage, no Python coverage over the large `scripts/`+`tests/` policy
  suite).
- No changelog, no release notes, no `RELEASES`/`CHANGELOG` document; a
  visitor cannot answer "what changed in v0.1.3?" without diffing history.
- Package pages have no curated description/README context beyond defaults
  (UNKNOWN how much GHCR renders for these packages; page-level curation is
  a Phase G work item).

## 4. Recommendations (for owner acceptance; no changes made here)

1. Semantic versions become the primary human identity everywhere (Phase G
   as planned): never publish `sha-*`/`sha256-*` as human tags from the new
   site repositories; preserve commit SHAs in OCI
   labels/annotations/attestations instead.
2. Introduce GitHub Releases + concise changelog in the site repositories
   from their first external release (v0.1.4+, strict bump per ADR 0014).
3. Coverage + badges (owner directive 2026-08-10): wire test coverage into
   CI for all three repositories and surface Actions status + coverage
   badges in each README, strictly zero-spend (no external badge accounts;
   GitHub-native workflow badges plus a repo-served coverage indicator).
   Design lands as its own reviewed CI change.
4. Historical GHCR cleanup (the existing `sha-*` clutter) remains an
   owner-executed action after new semantic releases are verified; this
   audit only inventories it.
5. The monorepo publishers freeze naturally at cutover; their final state
   should be documented in the cutover PR rather than redesigned now.
