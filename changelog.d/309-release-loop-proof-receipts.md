### Changed

- Give a promotion pull request a receipt it EARNS rather than one it requests. After planning, each tick judges every open promoter pull request it keeps by five proofs: novelty — no validator-shaped `snaraj-agent-reviews[bot]` receipt already binds that head; identity — the head commit's author and committer are the owner's noreply identity and its SSH signature verifies against the owner's registered keys; confinement — every path the head changes against `main` is one the promoter's own `apply_promotion` writes, the permitted set being that function's return value from the re-derivation, never a list kept in the tool; re-derivation — re-running the issue-195 acquisition ceremony from `main` in a detached read-only worktree re-renders the whole promotion surface, whose every tree entry is then compared to the head's by mode, type and Git object id; and claim audit — the pull request body and the head commit's message re-compose from those records and the head's own accounting. All five hold and the reviewer App posts `VERDICT: APPROVE` at that exact head, validated by `scripts/validate_review_receipt.py` and with the live head re-read before the token is minted and again immediately before posting; a definitive failure of identity, confinement, re-derivation or claim audit posts `VERDICT: REQUEST-CHANGES` naming that proof and only that proof. A head is judged only while its pull request is open, Draft and wears the `requires-review` the promoter armed at the cut — it never re-arms that label — and the tuple is re-read before the token is minted and again immediately before posting. The receipt binds the digest of the body it audited as `BODY-SHA256:`, which `scripts/ready_check.py` recomputes from the live body at flip time, withholding Ready on a body edited afterwards at the same head. A refusal the tool cannot attribute to the pull request — registry, Release, cosign, network — is neither verdict: it is logged and the head is judged again next tick. `receipt` runs the same step alone under the same lock.
- Stop arming the cybersecurity lane on the promoter's own mechanical output. `REVIEW_LABELS` is `("requires-review",)` and `scripts/ready_check.py`'s `PROMOTER_TUPLE` drops `cybersecurity-review-requested` with it; the tier/review pair rule now applies to ordinary authors only, where it was written to apply, since the promoter's exact tuple already fixes both members. The security lane keeps reviewing every change to the promoter's CODE, which is where the risk lives, and AGENTS.md's promoter paragraph states the new rule: the receipt is earned by re-derivation and posted by the App from the tick, Ready is still the coordinator's — "NO TOOL FLIPS READY, promoter included" is unchanged — and the owner alone merges.
- Keep the reviewer App's token out of everything but one process's environment. The helper that mints it is named by `PROMOTER_RECEIPT_TOKEN_COMMAND`, never by a committed path, and the launchd installer plants that variable only when told to; unset, the receipt step reports itself unconfigured and composes nothing. The token is minted, held in one local name and handed to exactly one `gh pr comment` subprocess through its environment — never an argument, never a log line, never a file — and a test asserts all three. The App's actor identity is read from `scripts/ready_check.py` rather than copied, so the principal the receipt is posted by and the principal the Ready rule later looks for cannot drift apart. Path names from an untrusted head are sanitized and bounded before they can reach a public comment.
- The promoter's receipt now audits the pull request body and the head commit's message by re-composing both from the re-derived records; verifies the head commit's SSH signature against the owner's registered keys and its author and committer against the owner's noreply identity before attesting it; compares every promotion-surface tree entry by mode and type as well as object id; counts only a validator-shaped App receipt as binding a head and re-reads both the head and the receipt set after the token is minted, immediately before posting; retires `requires-review` with either verdict and finishes a retirement a failed write left undone on the next tick, at that head only, never re-arming it; and traces the tick's first fetch and cosign's version check like every other call.
